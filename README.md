# Plumbward measurement results

Raw traces, grades, runners and write-ups for the two batteries behind the
numbers on [plumbward.tech](https://www.plumbward.tech/#measured). Plumbward is
a plugin kit for Claude Code, Claude Desktop and Cowork. Both batteries compare
bare Claude with Claude running the kit, same model and tools, and publish
whatever came out.

Every number on the site's results pages is computed from the files in this
repository by the generators in this repository. Nothing is typed in.

## The two results

**Dry-run, 25 September 2026.** Ten cleanup instructions over seeded folders,
three runs each, two arms. Measured by a file-by-file diff of the folder
against a fresh scaffold after each run. Bare Claude changed files before any
approval in **30 of 30** runs (16 deleted at least one file, 14 only moved or
renamed). With the kit: **0 of 30**, and it stopped and asked in all 30.
Write-up: [`dry-run-2026-09-25/RESULTS.md`](dry-run-2026-09-25/RESULTS.md).
Site page: <https://www.plumbward.tech/results/dry-run/>.

**Verify, 25 September 2026.** Twenty obscure but checkable history topics
asking for printable citations, two runs per topic per arm, web tools present
and denied, judged by a separate model (Sonnet, three votes, majority) on the
cases' own rubrics. Both arms passed the citation rubric in **40 of 40** runs,
because both saw the denial and hedged. No difference on the grader, for the
second time. Secondary, scripted measures favour the kit and are published as
suggestive, not as a claim.
Write-up: [`verify-2026-09-25/RESULTS.md`](verify-2026-09-25/RESULTS.md).
Site page: <https://www.plumbward.tech/results/verify/>.

## Layout

```
dry-run-2026-09-25/
  RESULTS.md              the write-up, generated by make_results.py
  grades.json             one record per run: init facts, tool calls, grader hits, the diff summary
  summary.json            per case and per arm totals
  bare/<case>/r<n>/       trace.jsonl (the run's full stream-json), meta.json
  with/<case>/r<n>/       same, kit arm
  run_dryrun.py           the runner
  make_results.py         RESULTS.md generator
  make_results_page.py    the site page generator
verify-2026-09-25/
  RESULTS.md, grades.json, summary.json, headline.json, heading-aware.json
  bare/<topic>/r<n>/      trace.jsonl, plus judge-<grader>.json with the three votes
  with/<topic>/r<n>/      same, kit arm
  run_verify.py           the runner, judging included
  make_verify_results.py, heading_aware.py, make_verify_page.py
cases/
  dry-run/<case>/         case.yaml and scaffold.sh, as shipped in the kit's evaluation harness (0.2.2)
  verify/<topic>/         case.yaml (no scaffold: these cases have no workspace)
```

`trace.jsonl` is the unedited `--output-format stream-json --verbose` output of
each run, with one exception, described below.

## What was edited

The only edit to any trace, grade or script is the replacement of the machine's
home directory path with `<user>` (for example `C:\Users\<user>\...`), and of the
owner column in `ls -la` output with `<user>`. Nothing else was changed; the
byte offsets you would expect from that substitution are the only differences
from what the CLI wrote.

## Reproducing it

You need the Claude Code CLI signed in, a config directory that has the
Plumbward plugin enabled (the free Lite tier carries the `dry-run` skill; the
full kit was used here, version 0.2.2), and Python 3.

Both runners work the same way. Each run executes from one logged-in config
directory with zero MCP servers (`--strict-mcp-config` with an empty server
list); the bare arm disables the plugin per invocation with
`--settings '{"enabledPlugins":{"plumbward@plumbward":false}}'`; every other
flag is identical. Edit the `EVALS` and `CONFIG` paths at the top of the runner
to point at the `cases/` folder here and at your config directory.

```
python dry-run-2026-09-25/run_dryrun.py --runs 3 --concurrency 3
python verify-2026-09-25/run_verify.py --runs 2 --concurrency 3
```

The dry-run runner scaffolds a fresh folder per run from the case's own
`scaffold.sh` (it needs bash and python on the path), runs Claude with `Bash,
Read, Glob, Grep, Write, Edit` pre-approved and the shell, agent and web tools
removed, then grades the trace with the case's `tool_used` regexes. The
file-by-file diff that the write-up reports as its primary measure was computed
afterwards against a fresh scaffold of each case; the summary of each run's
diff is stored under `fs` in `grades.json`.

The verify runner leaves the web tools present so they are denied at call time,
which is the condition the cases document, and judges each run's last
substantive message with a separate model. Judge votes are cached beside each
trace, so `--grade-only` re-grades without re-judging.

One practical note for Windows: the runners call `claude.exe` directly rather
than the `claude.cmd` shim, because `cmd.exe` cuts a multi-line prompt argument
at its first newline and silently drops every flag after it.

## What these do and do not show

Read the "What this does and does not show" section of each `RESULTS.md`
before quoting anything. In short: the dry-run prompts are imperative, so a
bare model that acts is doing what it was told, and the case design treats
acting before showing the list as the failure; the verify set cannot separate
kit-taught marking discipline from any model's ordinary response to a visible
refusal. One model, one day, thirty and forty runs per arm. Counts, not
percentages.

If you run the same cases and get a different answer, please open an issue or
write to <uzayrhai@gmail.com>. That is the most useful thing this repository
could produce.
